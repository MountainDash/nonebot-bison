# 配置由组件声明 schema，配置系统不单独成包

bison 的配置系统是 **bison 内部的一个模块**，不是一个包。它读一份 toml，由各组件**声明自己的 pydantic 模型**，loader 按组件 id 组装并校验。粒度是三层：组件默认、源级覆盖、订阅级覆盖。凭证（cookie）是**数据**不是配置，留在存储里，配置只描述用哪个凭证与如何轮换。

**为什么不分包**：包边界应由**依赖集合**与**发布节奏**决定，不由体积决定。配置系统的依赖（pydantic、tomllib）与 bison 其余部分完全相同，没有独立发布的需求，也没有第二个消费者；而它与注册中心是互相咬合的（配置 schema 要注册进去，配置里的组件名要对照注册表校验），拆开只会制造一条 `config → registry` 的跨包依赖。

## Considered Options

- **一个全局配置模型、所有字段平铺**（现状：19 个 `PlugConfig` 字段）：加一个平台就加几个字段，配置与组件无法各自演进。
- **每个组件自己读文件**：校验时机分散，拼错组件名会被静默忽略。
- **独立的配置包**：见上。

## Consequences

- 校验失败要报到「哪个组件的哪一段哪一行」，而不是一个 `ValidationError` 加一坨 JSON。
- 配置里出现一个未注册的组件名**必须报错**（现状是静默忽略）。
- 配置 schema 进注册中心，于是网页可以自动生成表单、inspect 可以显示「这个组件接受哪些配置项」—— 这是注册中心白拿的第三样东西。
- 「目的地级配置」不做：真实需求（不同群想要不同风格）由订阅级表达，而 50 个目的地上的例外会扩散成 50 份需要维护的特例。
