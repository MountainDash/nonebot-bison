# 运行 — 进程、网页、可观测、迁移、容量

## 1. 进程与启动顺序

**单进程。** NoneBot 的 asyncio loop 同时承载对话、网页与 courier 循环。

```
NoneBot 加载全部插件（含所有专线包）
      ↓
bison 收集注册、构造 CourierConfig、构造 courier
      ↓
一次性校验（全部缺失项一起报）        ← 失败即拒绝启动
      ↓
courier.run()                        ← 从这一刻起注册表冻结
```

**为什么必须先加载完再校验：** NoneBot 的 `available_plugins` 是 `set`，`load_all_plugins` 按集合迭代 —— 插件加载顺序不确定。若 courier 先启动而组件后注册，第一批投递会全部因为没有对应站点而进回收站（`routing` 错），而那是**假错误**：地址是对的，只是注册还没到。

**冻结的边界：** 只是禁止**运行时动态注册**。安装子包 → 加载 → 注册，全部发生在冻结之前，所以扩展不受影响。

宿主侧承载约束：courier 循环必须放在可取消的 task group 里（`driver.task_group` 或 anyio 等价物），不能用裸 `asyncio.create_task`，否则 NoneBot 关闭时它不会被取消。

## 2. 关闭

NoneBot 的关闭是「反序执行 `on_shutdown` 然后硬 cancel」。因此 `on_shutdown` 里必须显式 `courier.close()` 并等待排干（默认 10s）。

未排干的包裹留在信道里，重启后继续。唯一无法消除的窗口见 [0001 §12](./0001-courier.md)。

## 3. 网页

- **同进程**挂在 `driver.server_app` 上（旧代码的 `/bison` 子应用模式可复用）。
- **复用旧 admin 的 JWT 与权限模型**（群权限 / 超管）。
- **重写 API。** 旧的 16 条路由全部按 `(groupNumber, platformName, target)` 三件套写死；其中 `GET/PUT /weight` 直接暴露了加权轮询的权重，那是把实现细节泄漏成用户配置，新设计里加权轮询已不存在，这条路由应当消失。
- **写操作严格白名单**：只允许幂等动作（重试一条死信、暂停一条订阅、刷新源名字）。改配置、改订阅关系走对话命令或改文件 —— 同进程意味着一次同步阻塞或死锁就是整个 bot 掉线。
- **前端先审计再决定改造程度。** 旧 SPA 在 v0.6 重写过、v0.7 又改过，是考古记录里的负担来源。
- **排期靠后不影响内核：** 现在只需要把 inspect 的数据结构定死（[0002 §13](./0002-bison.md)），前端何时做都不改变内核。

## 4. 可观测与告警

指标由 bison 侧暴露（Prometheus），courier 只发事件、不认 Prometheus。

**最小指标集：**

| 指标 | 用途 |
|---|---|
| `channel_head_age_seconds{resource}` | 积压与卡死的第一信号 |
| `dead_letter_count{reason_kind}` | 分「临时 / 凭证 / 永久 / 路由 / 扇出超限」 |
| `fetch_outcome{source, result}` | 抓取成功率与风控 |
| `enricher_failures{enricher}` | 可选富化器的健康度 |
| `render_duration{renderer}` | 渲染仍是热点，旧指标集保留 |
| `degradation_count{subscriber, kind}` | 渲染降级与发送器能力不足 |

**死信要主动通知管理员**（私聊或网页红点）。现在的模式是靠用户来报「我的订阅没动静了」——那是把监控外包给用户。

## 5. 迁移

**独立插件，不进运行时。** 两个入口一份代码：`nb bison-migrate` 子命令 + `python -m bison_migrate`。

**要做两场迁移：**

1. **数据**：旧 6 张表（`User` / `Target` / `Subscribe` / `ScheduleTimeWeight` / `Cookie` / `CookieTarget`）+ `nbesf` v1/v2/v3 → 新 schema。
2. **基础设施**：`nonebot-plugin-datastore` 提供的 SQLite → `nonebot-plugin-orm`（Alembic）。旧库与新库可能不在同一个文件，所以「一个事务搬完」不成立 —— 必须能中断重跑。

**三条硬约束：**

1. **绝不删旧表。** 只读旧表、写新表。旧代码曾经在启动时 `drop()` 掉 tinydb 文件，不要重犯。
2. **不伪造去重游标。** 旧系统的去重状态在内存里，迁移无法恢复。首轮**静默初始化**（只记录游标、不发送），并告知「已接管 N 条订阅」。
3. **绝不伪造历史。** 迁移不生成任何「已投递」记录。

**检测机制（最小化旧 schema 知识）：** 迁移成功后写一行标记 `logistics_meta.migrated_from = "nonebot-bison@<version>"`。新 bison 启动时只做一次前置检查：**存在 `nonebot_bison_` 前缀的表、但没有迁移标记 → 拒绝启动并提示先迁移**。一个常量 + 一次查询，不是迁移知识。

**已知取舍：** 静默初始化等于主动丢一次（与「不丢 > 不乱 > 不重」冲突）。理由是迁移是一次性事件，而「50 个群同时收到旧动态」是立刻可见的伤害，「接管前那几条没收到」是不可见的损失，且与旧行为一致（`BISON_INIT_FILTER` 默认就是静默初始化）。

## 6. 容量与 GC

**渲染产物**（Claim Check）落 cache 目录，队列里只放引用。

- **只存渲染产物；原始媒体在渲染时下载一次**（因为要合成卡片），此后投递不再依赖 CDN —— 这同时消灭了图床防盗链那一类故障。
- **保留期由「引用它的所有包裹都 settled」决定**，不是「这一条发了」。扇出之后同一张卡片被 N 个目的地引用，第 3 个还在重试时第 1 个已经发完。
- GC 三重条件：所有引用 settled 后立即删 / 放弃后 3 天 / 全局 7 天，另加总容量上限 5GB（LRU，优先删已投递最久的）。

**量级估算：** 500 条/天 × 单张卡片 ~300KB ≈ 150MB/天；连原始媒体一起 ≈ 900MB/天。所以「渲染时下载、投递后删」不是优化，是必需。

**补发积压：** 上限 24 小时 / 200 条。超出部分进终局区，并给该目的地发一条「积压过多，已丢弃 N 条」的提示 —— 对一个群来说，静默丢 500 条比丢 500 条还附一句解释更糟。

## 7. 已知风险

| 风险 | 处置 |
|---|---|
| 「send 返回后、mark 前」进程死掉 → 重发一次 | 接受；聊天平台无幂等键，无法消除 |
| 插件加载顺序不确定 | 加载完再校验，一起报错 |
| 长开关的 datastore → orm 迁移 PR | 迁移做成独立插件，先发 0.1 只支持主路径 |
| 子包与 bison 的版本漂移 | `bison_api_version` + 启动期校验 |
| 静默降级 | 每次降级记 metric 与 `extra`，inspect 可见 |
| 扇出放大 | 后代总量预算 200，超限进回收站 |
| 网页阻塞主循环 | 写操作白名单 + 禁止同步阻塞 |
