# Courier prior art: routing, ordering, retry, dead-lettering

Scope: message-routing core that moves "parcels" through ordered per-destination pipelines with relay stations, terminal stations, and dead-letter handling. Everything below is mechanism-level and cited. `[FACT]` = stated by the cited source. `[OPINION]` = my judgement, marked as such.

## A. Enterprise Integration Patterns (Hohpe & Woolf)

Catalogue index for the whole set: [enterpriseintegrationpatterns.com/eaipatterns.html](https://www.enterpriseintegrationpatterns.com/eaipatterns.html).

- **Message Router** — A special filter that consumes a message from one channel and republishes it to a different channel depending on a set of conditions; it connects one input to *multiple* output channels and, per the catalogue, "does not modify the message contents. It only concerns itself with the destination." The benefit is that destination criteria live in one place, and because every message passes through the single router, "incoming messages are guaranteed to be processed one-by-one in the correct order." ([MessageRouter.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageRouter.html))

- **Routing Slip** — "Attach a Routing Slip to each message, specifying the sequence of processing steps. Wrap each component with a special message router that reads the Routing Slip and routes the message to the next component in the list." A component at the head of the flow computes the step list per message, attaches it, and routes to step 1; each step then reads the slip and forwards to the next step named in it. The itinerary is *message data*, carried with the parcel, and the pattern explicitly assumes the sequence is determined up-front and linear. ([RoutingTable.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RoutingTable.html))

- **Process Manager** — Used precisely when Routing Slip's two assumptions fail (steps unknown at design-time, or non-linear/parallel): "Use a central processing unit, a Process Manager, to maintain the state of the sequence and determine the next processing step based on intermediate results." Each processing unit replies to the Process Manager, which decides and dispatches the next step — a hub-and-spoke flow whose downside is "the danger of turning the Process Manager into a performance bottleneck"; the catalogue also warns that using one everywhere "may be overkill." ([ProcessManager.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html))

- **Routing Slip vs Process Manager (who owns the itinerary)** — `[FACT]` In Routing Slip the *sender* owns the itinerary and it travels inside the message; each station only knows "next", and no component has global state. In Process Manager a *central component* owns the itinerary; the message carries no plan, stations reply to the hub, and only the hub knows what has happened so far. The catalogue frames the choice purely as: fixed/linear plan ⇒ slip; decisions depending on intermediate results or parallelism ⇒ manager. ([RoutingTable.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RoutingTable.html), [ProcessManager.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html))

- **Dead Letter Channel** — "When a messaging system determines that it cannot or should not deliver a message, it may elect to move the message to a Dead Letter Channel"; concrete behaviour is implementation-defined. The catalogue's key structural claim: "Typically, each machine the messaging system is installed on has its own local Dead Letter Channel so that whatever machine a message dies on, it can be moved from one local queue to another without any networking uncertainties," and moving the message "may also record the original channel the message was supposed to be delivered on." ([DeadLetterChannel.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/DeadLetterChannel.html))

- **Idempotent Receiver** — "Design a receiver to be an Idempotent Receiver — one that can safely receive the same message multiple times," because "even when a sender application only sends a message once, the receiver application may receive the message more than once." The catalogue names exactly two implementation routes: explicit de-duping (removal of duplicate messages) or defining message semantics so re-application is harmless. ([IdempotentReceiver.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/IdempotentReceiver.html))

- **Message Store** — Capture information about each message in a central location, without disturbing the transient, loosely-coupled message flow: send a duplicate of the message to a special channel collected by the store, either from the component itself or via a Wire Tap; the secondary channel can be considered part of the Control Bus. Because it is fire-and-forget it does not slow the main flow but does add traffic, so you may store only key fields (message ID, channel, timestamp) rather than whole payloads. ([MessageStore.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageStore.html))

- **Claim Check** — "Store message data in a persistent store and pass a Claim Check to subsequent components." Five-step mechanism: data arrives; a "Check Luggage" component generates a unique key; it extracts the data into a persistent store and associates it with the key; it removes the data from the message and adds the Claim Check; a later component uses Content Enricher to retrieve the data by key. Purpose: reduce message volume on the wire without losing information. ([StoreInLibrary.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/StoreInLibrary.html))

- **Message Sequence** — For payloads too large for one message: "send the data as a Message Sequence and mark each message with sequence identification fields," namely *sequence identifier* (which cluster), *position identifier* (order within cluster), and *size or end indicator* (count, or marks the last message whose position then gives the size). ([MessageSequence.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageSequence.html))

- **Resequencer** — "Use a stateful filter, a Resequencer, to collect and re-order messages so that they can be published to the output channel in a specified order." Mechanism: an internal buffer holds out-of-sequence messages "until a complete sequence is obtained," then in-sequence messages are published; crucially "it is important that the output channel is order-preserving." The problem it solves is that messages routed by different paths arrive at different times, breaking order for steps that need in-sequence processing (e.g. referential integrity). ([Resequencer.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/Resequencer.html))

- **Resequencer timeouts (what the pattern prose does not fix)** — `[FACT]` The catalogue page specifies buffering and the order-preserving output channel but names no timeout, capacity, or gap-release policy; production implementations must pick one. Apache Camel's stream mode does gap detection on sequence numbers with a bounded backlog (default capacity 1000) and a `timeout()`: "in case of a timeout, then the resequencer disregards the current expected sequence number, and moves to the next expected number," with `rejectOld()` to refuse late arrivals outright; batch mode collects up to `batchSize` (default 100) or `batchTimeout` (default 1000 ms), sorts, then emits. ([camel.apache.org/.../resequence-eip.html](https://camel.apache.org/components/latest/eips/resequence-eip.html)) Spring Integration exposes the same policy space as configuration: `group-timeout`, `release-partial-sequences`, `send-partial-result-on-expiry`, `expire-group-upon-timeout`, and warns the resequencer "is intended to resequence relatively short sequences of messages with small gaps." ([docs.spring.io/.../resequencer.html](https://docs.spring.io/spring-integration/reference/resequencer.html))

- **Correlation Identifier** — Each reply carries "a unique identifier that indicates which request message this reply is for," copied from the request's request ID by the replier; the six named parts are requestor, replier, request, reply, request ID, correlation ID. It exists because Request-Reply over messaging has no call stack to match replies against. ([CorrelationIdentifier.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CorrelationIdentifier.html))

- **Channel Adapter** — "Use a Channel Adapter that can access the application's API or data and publish messages on a channel based on this data, and that likewise can receive messages and invoke functionality inside the application." It acts as a messaging client to the bus and invokes application functions through an application-supplied interface, and may attach at different layers of the application's architecture. ([ChannelAdapter.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ChannelAdapter.html))

- **Composed Message Processor** — For a composite message whose elements each need different handling: "splits the message up, routes the sub-messages to the appropriate destinations and re-aggregates the responses back into a single message," using an Aggregator to reconcile replies from the multiple processing units. ([DistributionAggregate.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/DistributionAggregate.html))

- **Scatter-Gather** — "Broadcasts a message to multiple recipients and re-aggregates the responses back into a single message," then uses an Aggregator to distill them. Two dispatch variants: a Recipient List (you control and must know each recipient's channel) or auction-style via Publish-Subscribe Channel (one channel, but you relinquish control of who answers). ([BroadcastAggregate.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/BroadcastAggregate.html))

- **Wire Tap** — "Insert a simple Recipient List into the channel that publishes each incoming message to the main channel and a secondary channel" — a fixed two-output Recipient List that consumes from the input and republishes the *unmodified* message to both. Because analysis logic lives in the second component, you can insert it into any channel "without any danger of modifying the primary channel behavior." ([WireTap.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/WireTap.html))

- **Aggregator (the pattern Resequencer is built from)** — "A stateful filter [that] collects and stores individual messages until a complete set of related messages has been received," then publishes one distilled message. Design requires three decisions: correlation (which messages belong together), completeness condition, aggregation algorithm. The catalogue enumerates the completeness conditions and their costs — "Wait for All" (needs a timeout or "a single missing or delayed message will prevent further processing of the whole aggregate"), "Time Out", "First Best", "Time Out with Override", "External Event." ([Aggregator.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/Aggregator.html))

- **Sequential Convoy** — "Group related messages by a category key and process each group sequentially, one message at a time, while processing different groups in parallel." Mechanism: the broker partitions by category key and enforces FIFO inside a group; a consumer takes an exclusive lock on a group (Azure Service Bus *sessions* are the reference implementation) and receives that group's messages strictly in enqueue order while other consumers take other groups. The page documents the sharp edges that matter for a courier: throughput per group is bounded by single-message processing time; messages may arrive out of order *before* broker session ordering applies (use sequence numbers or an end-of-sequence flag); and "a message that repeatedly fails processing within a session blocks all subsequent messages in that session," so delivery-attempt counts plus a dead-letter threshold are mandatory. ([learn.microsoft.com/.../sequential-convoy](https://learn.microsoft.com/en-us/azure/architecture/patterns/sequential-convoy)) `[FACT]` I could not find this pattern in the EIP online catalogue (`SequentialConvoy.html` 404); the Azure page is the clearest primary description I located.

## B. AMQP 0-9-1 / RabbitMQ semantics

- **Model: exchange → binding → queue** — Producers publish to an exchange; queues are bound to exchanges; the exchange type plus the routing/binding key decides which queues receive a copy. A binding is a rule with an optional argument map that "certain exchange types can use (e.g. the headers exchange)," and bindings themselves have durability. ([rabbitmq.com/docs/exchanges](https://www.rabbitmq.com/docs/exchanges), [rabbitmq.com/tutorials/amqp-concepts](https://www.rabbitmq.com/tutorials/amqp-concepts))

- **Direct exchange** — "routes to one or more bound queues, streams or exchanges using an exact equivalence of a binding's routing key," e.g. binding key `abc` matches `abc` and only `abc`. `[FACT]` The default exchange is a direct exchange with special properties that lets you publish to a queue by name without declaring a binding. ([rabbitmq.com/docs/exchanges](https://www.rabbitmq.com/docs/exchanges))

- **Topic exchange** — Pattern matching of the routing key against the binding pattern, with keys split into dot-separated segments and two wildcards: `*` for exactly one segment, `#` for zero or more. So `regions.na.cities.*` matches `regions.na.cities.toronto` but not `regions.na.cities`, and binding `#` alone makes the topic exchange behave as a fanout for that binding. ([rabbitmq.com/docs/exchanges](https://www.rabbitmq.com/docs/exchanges))

- **Fanout exchange** — Routes "a copy of every message published to them to every queue, stream or exchange bound to it. The message's routing key is completely ignored." ([rabbitmq.com/docs/exchanges](https://www.rabbitmq.com/docs/exchanges))

- **Headers exchange** — Routes on header values, not the routing key, and needs one extra decision expressed as the `x-match` binding argument: `any` (one matching header suffices) or `all` (all must match); by default headers beginning with `x-` are excluded from matching unless `x-match` is `any-with-x`/`all-with-x`. The docs describe it as "direct exchanges on steroids" because the routing key need not be a string. ([rabbitmq.com/tutorials/amqp-concepts](https://www.rabbitmq.com/tutorials/amqp-concepts))

- **Queue ordering guarantee (the exact scope)** — "A queue is an ordered collection of messages providing FIFO semantics… When publishing on a single channel, messages are enqueued in publishing order in every queue they are routed to. When publishing happens on multiple connections or channels, their sequences of messages will be routed concurrently and interleaved. Delivery from a queue to consumers proceeds in enqueue order." Note the boundary: the guarantee is *per queue*, and only *per publishing channel* on the ingress side. ([rabbitmq.com/docs/queues#message-ordering](https://www.rabbitmq.com/docs/queues))

- **When RabbitMQ reorders (documented)** — Two named causes: message priorities ("higher-priority messages may be delivered before lower-priority messages"), and "multiple active consumers on the same queue: the broker still dequeues in FIFO, but any redelivery can change order. Redelivery happens when consumers negatively acknowledge with requeue or a channel/session closes with unacked messages. Redelivered messages are flagged (AMQP 1.0: `first-acquirer=false`, AMQP 0-9-1: `redelivered=true`)." This is the documented warning you were asking about. ([rabbitmq.com/docs/queues#when-messages-can-be-reordered](https://www.rabbitmq.com/docs/queues))

- **Preserving order with queues (documented recipe)** — Use a stream, or a queue with a single active consumer plus: return messages in the order received; for quorum queues set a delivery limit; "AMQP 0-9-1: don't use `basic.get`. When stopping a consumer, prefer closing the channel over `basic.cancel`"; and to get concurrency *and* per-entity order, "use the `x-modulus-hash` exchange to partition messages across multiple queues, each with a single active consumer." ([rabbitmq.com/docs/queues#preserving-message-order](https://www.rabbitmq.com/docs/queues))

- **Prefetch / QoS** — AMQP 0-9-1's `basic.qos` limits unacknowledged deliveries, but RabbitMQ "slightly deviates from the AMQP 0-9-1 spec": the spec's `prefetch_count` is "shared across all consumers on the channel," whereas RabbitMQ applies it "separately to each new consumer on the channel." `basicQos(0)` means no limit. The rationale given is cost: channel-scoped prefetch requires channel/queue coordination per message, "very slow when consuming across a cluster." ([rabbitmq.com/docs/consumer-prefetch](https://www.rabbitmq.com/docs/consumer-prefetch))

- **Prefetch is the only real backpressure knob** — "Manual acknowledgement mode is typically used with a bounded channel prefetch which limits the number of outstanding ('in progress') deliveries on a channel. With automatic acknowledgements, however, there is no such limit by definition," so consumers can be overwhelmed and "run out of heap." The doc also notes a prefetch of 2,000 "won't be meaningfully different from that of 300" for throughput. ([rabbitmq.com/docs/confirms](https://www.rabbitmq.com/docs/confirms))

- **Publisher confirms** — Enable with `confirm.select` (channel enters "confirm mode"; a transactional channel cannot be put into confirm mode and vice versa); broker and client then count messages from 1 and the broker acks each handled message on the same channel. Motivation: "Using standard AMQP 0-9-1, the only way to guarantee that a message isn't lost is by using transactions… transactions are unnecessarily heavyweight and decrease throughput by a factor of 250." Confirms and consumer acks are "entirely orthogonal and unaware of each other." ([rabbitmq.com/docs/confirms](https://www.rabbitmq.com/docs/confirms))

- **Consumer acks, nack/reject, requeue** — `basic.ack` positive, `basic.nack` negative (a RabbitMQ extension, can reject multiple at once), `basic.reject` negative but single; the `requeue` field decides discard / dead-letter / requeue. `basic.nack`'s `multiple` flag acks everything up to a delivery tag (tags 5–8 ⇒ 5..8 acked). Autocompact mode ("fire-and-forget") is "unsafe and not suitable for all workloads" because messages are considered delivered when written to the socket. ([rabbitmq.com/docs/confirms](https://www.rabbitmq.com/docs/confirms))

- **Why requeue replay is not a retry mechanism** — Three documented properties kill it: (1) position: "When a message is requeued, it will be placed to its original position in its queue, if possible. If not (due to concurrent deliveries and acknowledgements from other consumers when multiple consumers share a queue), the message will be requeued to a position closer to queue head." (2) immediate availability: "Requeued messages may be immediately ready for redelivery depending on their position in the queue and the prefetch value… if all consumers requeue because they cannot process a delivery due to a transient condition, they will create a requeue/redelivery loop," which is "costly in terms of network bandwidth and CPU." (3) no delay, no attempt budget of its own: only quorum queues count `basic.reject` toward a delivery limit, and since RabbitMQ 4.3 `basic.nack`-with-requeue does *not* count, so nail-with-requeue "can be redelivered indefinitely." ([rabbitmq.com/docs/confirms#negative-acknowledgement-and-requeuing-of-deliveries](https://www.rabbitmq.com/docs/confirms), [rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))

- **Dead-letter exchange (DLX): the four triggers** — A message is dead-lettered when (a) rejected with requeue=false, (b) it expires (per-message/queue TTL), (c) queue length limit exceeded, or (d) delivery limit exceeded (quorum queues). `[FACT]` If an entire queue expires, its messages are *not* dead-lettered. ([rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))

- **DLX is a per-queue property, not a broker or exchange property (the "private to the queue" caveat)** — Dead-lettering is configured either as queue arguments (`x-dead-letter-exchange`, `x-dead-letter-routing-key`) or as a policy whose `dead-letter-exchange` key is applied to queues (`--apply-to queues`). There is no exchange-level or global DLX switch, so every queue that needs one must be declared/policy-covered individually, and permissions are checked at queue-declare time (configure on the queue, read on the queue, write on the DLX). ([rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))

- **x-death headers** — Dead-lettering rewrites the message: exchange name replaced by the latest DLX, routing key possibly replaced, CC removed (and BCC per sender-selected distribution). Each dead-letter event is recorded in an `x-death` array (AMQP 1.0: `x-opt-deaths`), ordered most-recent-first, with entries compressed by the `{Queue, Reason}` pair so the header does not grow unboundedly; each entry carries `queue`, `reason` (`rejected` / `expired` / `maxlen` / `delivery_limit`), `count`, `time`/`first-time`+`last-time`, `exchange`, `routing-keys`, and `original-expiration`. Six conveniences are added for the first event: `x-first-death-queue`, `x-first-death-reason`, `x-first-death-exchange`, plus `x-last-death-*` which are updated on each subsequent death. Note "the original message's TTL is removed from the message on dead-lettering to prevent it from expiring again in any queues it is routed to." ([rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))

- **DLX durability is not free** — "By default, dead-lettered messages are re-published without publisher confirms turned on internally. Therefore using DLX in a clustered RabbitMQ environment is not guaranteed to be safe" — the message is removed from the original queue immediately after publishing to the target, so it "can be lost if the target queue is not available." Quorum queues support at-least-once dead-lettering by publishing with confirms internally. RabbitMQ also detects a dead-letter cycle and drops the message "if there was no rejection in the entire cycle." ([rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))

- **TTL: two flavours and a head-of-queue trap** — Per-queue message TTL (queue argument/policy) and per-message TTL (`Expiration` property set by the publisher); a message routed to multiple queues "can expire at different times, or not at all, in each queue." `[FACT]` Expiry is lazy: "Only when expired messages reach the head of a queue will they actually be discarded (marked for deletion)," and "when setting per-message TTL expired messages can queue up behind non-expired ones until the latter are consumed or expired. Hence resources used by such expired messages will not be freed." There is also a delivery race: "a message can expire after it was written to the socket but before it has reached a consumer." ([rabbitmq.com/docs/ttl](https://www.rabbitmq.com/docs/ttl))

- **Quorum queues** — Replicated queues backed by a Raft-style quorum: "the majority of queue members (leader and followers) agree on the exact state of the queue and its contents." Intended for long-lived, HA, correctness-critical queues (the doc's own example is "incoming orders in a sales system"), not for every use case. They add: poison-message handling via `x-delivery-count`/`x-acquired-count` and a `delivery-limit` (default 20 since 4.0, `-1` disables), consumer timeouts, delayed messages, deferred messages, and delayed retry. ([rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))

- **Quorum delayed retry (the built-in backoff mechanism)** — Available since 4.3: returned messages are held in a delayed queue keyed by ready-at timestamp, with "linear back-off per queue," delay = `min(min_delay * delivery_count, max_delay)` (e.g. 1 s, 2 s, 3 s… capped at 30 s); configured via `x-delayed-retry-type` (`disabled`/`all`/`failed`/`returned`), `x-delayed-retry-min`, `x-delayed-retry-max` (queue args or policy). RabbitMQ's own guidance: "Quorum queues natively support delayed retry, which is the recommended approach for this use case," and dead-lettering "remains the right tool for messages that cannot be processed at all, for example, those that exceed the delivery limit." ([rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues), [rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))

- **Native delayed delivery and deferral (4.4)** — Publishers can set `x-opt-delivery-time` (future Unix ms) on AMQP 1.0 annotations or AMQP 0-9-1 headers: "Routing and replication happen immediately. The queue confirms the message once it is safely replicated, but only makes it available to consumers at the specified time. No plugin or queue argument is required." Separately, "an AMQP 1.0 consumer can defer a message until a prerequisite is ready, then explicitly retrieve it using a token" — settle with `modified` carrying `x-opt-deferral-token` plus `x-opt-delivery-time`; any consumer can later claim the token and get the messages "delivered ahead of the available backlog," oldest first, and at the deadline an unclaimed message "becomes available to all consumers again." This is the most direct broker-level primitive for "wait for the missing predecessor." ([rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))

- **Single Active Consumer (SAC)** — "Makes it possible to only have one consumer at a time consuming from a queue… useful when messages must be consumed and processed in the same order they arrive in the queue." Mechanism: the first registered consumer becomes active and "the other consumers are ignored"; on cancel/death another registered consumer becomes active (automatic failover); for quorum queues a newly-registered higher-priority consumer causes delivery to stop to the current one until outstanding messages are acked. "Without the single active consumer feature enabled, messages would be dispatched to all consumers using round-robin." ([rabbitmq.com/docs/consumers#single-active-consumer](https://www.rabbitmq.com/docs/consumers))

- **Consistent-hash exchange (`x-consistent-hash`)** — Exchange type that hashes a message property (usually the routing key) onto a ring; each bound queue occupies hash positions "depending on its binding weight" (a number-as-a-string argument). It hashes *routing keys*, not payloads: "all messages with the same routing key will go to the same queue." The caveat that matters for ordering: when queues are added or removed, "a given routing key now **may route to a different queue**" — affinity is stable only for a fixed topology. The README itself notes the sibling `rabbitmq-sharding` plugin trades "total stream ordering for processing parallelism." ([github.com/rabbitmq/rabbitmq-server .../rabbitmq_consistent_hash_exchange/README.md](https://github.com/rabbitmq/rabbitmq-server/blob/main/deps/rabbitmq_consistent_hash_exchange/README.md))

- **Delayed message plugin (`x-delayed-message`) and its documented limitations** — Declare an exchange of type `x-delayed-message` with `x-delayed-type` delegating routing to a normal exchange type, and publish with an `x-delay` header (milliseconds). Its README is blunt: "This plugin has serious limitations," delayed messages live "in a Mnesia table… with a single disk replica on the current node," the delivery timers "are not persisted" (re-initialised at plugin activation), only one copy exists in a cluster so "losing that node or disabling the plugin on it will lose the messages residing on that node," only one publish attempt is made, `mandatory` is unsupported, it "doesn't really fit scenarios with a high number of delayed messages (e.g. 100s of thousands or millions)," and disabling it loses all undelivered delayed messages. ([github.com/rabbitmq/rabbitmq-delayed-message-exchange README](https://github.com/rabbitmq/rabbitmq-delayed-message-exchange))

- **The TTL+DLX "delay queue" trick and its head-of-line problem** — Hohpe's write-up of scheduling messages in RabbitMQ documents the pre-plugin approach (`x-delay` on the plugin vs. TTL + DLX) and is the standard reference for why per-message delays built from queue TTL inherit the head-of-queue expiry semantics above. ([github.com/rabbitmq/rabbitmq-website blog: Scheduling Messages with RabbitMQ](https://github.com/rabbitmq/rabbitmq-website/blob/main/blog/2015-04-16-scheduling-messages-with-rabbitmq/index.md))

## C. Kafka ordering model

- **Ordering exists only inside a partition** — "Our topic is divided into a set of totally ordered partitions, each of which is consumed by exactly one consumer within each subscribing consumer group at any given time. This means that the position of a consumer in each partition is just a single integer, the offset of the next message to consume." There is no cross-partition order, and the "totally ordered" unit is the partition. ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design); source text: [docs/design/design.md](https://github.com/apache/kafka/blob/trunk/docs/design/design.md))

- **Key-based partitioning is how you buy per-key order** — "The client controls which partition it publishes messages to… it can be done by some semantic partitioning function… by allowing the user to specify a key to partition by and using this to hash to a partition. For example if the key chosen was a user id then all data for a given user would be sent to the same partition. This in turn will allow consumers to make locality assumptions about their consumption. This style of partitioning is explicitly designed to allow locality-sensitive processing in consumers." ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design))

- **Consumer-group rebalance perturbs that** — Partition assignment is the ordering mechanism *and* the scaling mechanism: "the way that consumer groups assign partitions to members of the group gives a powerful combination of ordering and scalability." A rebalance moves partitions between members; static membership exists precisely because dynamic membership "can cause a large percentage of tasks re-assigned to different instances during administrative operations such as code deploys, configuration updates and periodic restarts," and for stateful apps shuffled tasks "need a long time to recover their local states." ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design))

- **Idempotent producer: mechanism** — "The broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message," so resends do not create duplicate log entries; the KIP adds a producer epoch and specifies that the broker raises `OutOfOrderSequenceException` "if it receives a sequence number which is greater than the sequence it expected" — a fatal error, not a retryable one. ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design), [KIP-98](https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging))

- **Transactions + offset commit in one unit** — "it is only the producer which is transactional. It is however able to make transactional updates to the consumer's position (confusingly called the 'committed offset'), and it is this which gives the overall exactly-once behavior." Requirements: `isolation.level=read_committed`, `enable.auto.commit=false`, a `transactional.id` (which also aborts any in-flight transaction from a previous instance), and one producer per consumer instance to handle rebalances. On abort, "the application's state and in particular the current position of the consumer must be reset explicitly." ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design))

- **Transactional outbox** — You cannot have one transaction span the service DB and Kafka ("the latter doesn't support to be enlisted in distributed (XA) transactions"), so the outbox pattern writes the domain row and an outbox row in the *same local transaction*, then an async process (ideally log-based CDC) publishes outbox rows to Kafka; this gives "read your own writes" locally plus reliable eventually-consistent propagation. ([debezium.io blog: Reliable Microservices Data Exchange With the Outbox Pattern](https://debezium.io/blog/2019/02/19/reliable-microservices-data-exchange-with-the-outbox-pattern/))

- **Why "exactly-once" is end-to-end fiction** — `[FACT]` Kafka's own doc: "Exactly-once delivery for other destination systems generally requires cooperation with such systems, but Kafka provides the primitives which makes implementing this feasible… Otherwise, Kafka guarantees at-least-once delivery by default." The doc also warns that claims of exactly-once are often "misleading (i.e. they don't translate to the case where consumers or producers can fail, cases where there are multiple consumer processes, or cases where data written to disk can be lost)." ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design))

- **Log compaction** — "Log compaction ensures that Kafka will always retain at least the last known value for each message key within the log of data for a single topic partition," by "selectively remov[ing] records where we have a more recent update with the same primary key"; a null-payload record is a *tombstone* that deletes the key (and is itself cleaned out after the delete retention point). Compaction is background recopying of segments, does not block reads, and gives these guarantees: caught-up consumers see every message with sequential offsets (`min/max.compaction.lag.ms` bound the delay), and "Ordering of messages is always maintained. Compaction will never re-order messages, just remove some." Enabled per topic with `cleanup.policy=compact`. ([kafka.apache.org/documentation/#compaction](https://kafka.apache.org/documentation/#compaction))

## D. Erlang/OTP and the actor model

- **Mailbox is per-process; FIFO only per sender→receiver pair** — Every process has a message queue; "if an entity sends multiple signals to the same destination entity, the order is preserved; that is, if A sends a signal S1 to B, and later sends signal S2 to B, S1 is guaranteed not to arrive after S2." That is the *only* ordering guarantee — no global or cross-sender order. ([erlang.org/doc/system/ref_man_processes.html](https://www.erlang.org/doc/system/ref_man_processes.html))

- **Selective receive: mechanism** — A `receive` "searches for a message in the message queue that matches one of the patterns in the clauses… The first message from the start of the message queue that matches will be selected." The pattern that does not match is not consumed. Armstrong's description adds the machinery: the runtime "will look in the mailbox and try to match the first item… If no message matches then the received message is moved to a temporary 'save' queue and the process suspends and waits for the next message. If the message matches… any saved messages are put back into the input mailbox of the process." ([erlang.org/doc/system/expressions.html#receive](https://www.erlang.org/doc/system/expressions.html), [Armstrong thesis §3.3](https://erlang.org/download/armstrong_thesis_2003.pdf))

- **Selective receive: the cost, stated by the manual** — "The time complexity of a `receive` expression is O(N) where N corresponds to the number of messages preceding the matching message in the message queue. That is, when the combination of patterns of a `receive` expression only match specific messages and the message queue is huge, executing such a `receive` expression might become very expensive." The single documented optimization: create a reference and match on it in all clauses near creation, so "only the messages received after the reference was created need to be inspected." ([erlang.org/doc/system/expressions.html#receive](https://www.erlang.org/doc/system/expressions.html))

- **Why selective receive blows up memory** — `[FACT, mechanism]` Non-matching messages are *retained* in the queue (moved to a save queue and restored), so a process whose receive pattern waits for a specific message keeps every unrelated message resident while it waits; the scan cost is proportional to the head of the queue it must skip past. Armstrong lists "No control of the message queues" among the design errors to avoid and prescribes an `Other ->` catch-all clause in at least one receive statement per server "to avoid filling up message queues." ([erlang.org/doc/system/expressions.html#receive](https://www.erlang.org/doc/system/expressions.html), [Armstrong thesis §5.8–§5.9, §10](https://erlang.org/download/armstrong_thesis_2003.pdf))

- **Priority messages (OTP 28) change enqueue order deliberately** — A process may enable reception of priority messages; accepted priority messages are inserted after the last accepted priority message, so "two messages sent from the same sender may be in a different order from the order in which they were sent," while the signal ordering guarantee itself is unbroken. ([erlang.org/doc/system/ref_man_processes.html](https://www.erlang.org/doc/system/ref_man_processes.html))

- **Supervision strategies** — `one_for_one`: "If a child process terminates, only that process is restarted." `one_for_all`: "If a child process terminates, all remaining child processes are terminated. Subsequently, all child processes, including the terminated one, are restarted" (terminated right-to-left, restarted left-to-right). `rest_for_one` restarts the terminated child and everything started after it. `intensity`/`period` bound restart bursts, and exceeding them escalates the supervisor's own failure upward. ([erlang.org/doc/system/sup_princ.html](https://www.erlang.org/doc/system/sup_princ.html))

- **"Let it crash" as an error-recovery policy** — Armstrong's slogans: "Let some other process do the error recovery. If you can't do what you want to do, die. Let it crash. Do not program defensively." His distinction is the useful part: "exceptions occur when the run-time system does not know what to do; errors occur when the programmer doesn't know what to do" — if the programmer *does* know, trap and handle; otherwise crash and let the supervisor restore a known state. ([Armstrong thesis §4.3–§4.4](https://erlang.org/download/armstrong_thesis_2003.pdf))

- **Bounded mailbox / backpressure** — `[FACT]` OTP's process mailbox has no declarative capacity limit in the documentation; capacity control is a framework concern. Akka states the failure mode plainly: "By default an unbounded mailbox is used… in a scenario where messages are added to the mailbox faster than the actor can process them, this can lead to the application running out of memory. For this reason a bounded mailbox can be specified, the bounded mailbox will pass new messages to deadletters when the mailbox is full." Blocking-the-sender behaviour only appears with "other bounded mailbox implementations which will block the sender if the capacity is reached and configured with non-zero `mailbox-push-timeout-time`." ([doc.akka.io/.../typed/mailboxes.html](https://doc.akka.io/libraries/akka-core/current/typed/mailboxes.html))

- **Akka's ordering guarantee is exactly per sender–receiver pair** — The documented general rules are "at-most-once delivery, i.e. no guaranteed delivery" and "message ordering per sender–receiver pair." The rule "more specifically is that for a given pair of actors, messages sent directly from the first to the second will not be received out-of-order… The word *directly* emphasizes that this guarantee only applies when sending with the `tell` operator to the final destination, not when employing mediators." Causal transitivity across intermediaries does not hold. ([doc.akka.io/.../general/message-delivery-reliability.html](https://doc.akka.io/libraries/akka-core/current/general/message-delivery-reliability.html))

- **Mailbox type can silently break that guarantee** — "It is important to note that Akka's guarantee applies to the order in which messages are enqueued into the recipient's mailbox. If the mailbox implementation does not respect FIFO order (e.g. a `PriorityMailbox`), then the order of processing by the actor can deviate from the enqueueing order." Priority mailboxes: `UnboundedPriorityMailbox` (equal-priority order undefined) vs `UnboundedStablePriorityMailbox`, which preserves FIFO "for messages of equal priority." ([doc.akka.io/.../general/message-delivery-reliability.html](https://doc.akka.io/libraries/akka-core/current/general/message-delivery-reliability.html), [doc.akka.io/.../typed/mailboxes.html](https://doc.akka.io/libraries/akka-core/current/typed/mailboxes.html))

## E. What Spark's driver / cluster manager / worker architecture actually is

- **The components, in Spark's own words** — "Spark applications run as independent sets of processes on a cluster, coordinated by the `SparkContext` object in your main program (called the *driver program*)." The `SparkContext` connects to "several types of cluster managers (either Spark's own standalone cluster manager, YARN or Kubernetes), which allocate resources across applications"; it acquires executors on nodes, "which are processes that run computations and store data for your application," ships code to them, then "sends tasks to the executors to run." ([spark.apache.org/docs/latest/cluster-overview.html](https://spark.apache.org/docs/latest/cluster-overview.html))

- **Driver responsibilities** — Runs `main()`, creates the `SparkContext`, owns the DAG/scheduling of tasks, and in the RDD paper's phrasing: "The driver defines one or more RDDs and invokes actions on them. Spark code on the driver also tracks the RDDs' lineage." Operationally it "must listen for and accept incoming connections from its executors throughout its lifetime… the driver program must be network addressable from the worker nodes," and should sit close to the workers. ([spark.apache.org/docs/latest/cluster-overview.html](https://spark.apache.org/docs/latest/cluster-overview.html), [RDD paper, NSDI'12](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf))

- **Cluster manager responsibilities** — An "external service for acquiring resources on the cluster." Spark is deliberately "agnostic to the underlying cluster manager. As long as it can acquire executor processes… it is relatively easy to run it even on a cluster manager that also supports other applications." It allocates; it does not route messages or track work items. ([spark.apache.org/docs/latest/cluster-overview.html](https://spark.apache.org/docs/latest/cluster-overview.html))

- **Worker responsibilities** — A worker node is "any node that can run application code in the cluster"; an *executor* is "a process launched for an application on a worker node, that runs tasks and keeps data in memory or disk storage across them. Each application has its own executors." Executors "stay up for the duration of the whole application and run tasks in multiple threads," which isolates applications but means "data cannot be shared across different Spark applications… without writing it to an external storage system." ([spark.apache.org/docs/latest/cluster-overview.html](https://spark.apache.org/docs/latest/cluster-overview.html))

- **Fault tolerance is recomputation, not durable per-item state** — RDDs are recovered "using lineage"; "only the lost partitions of an RDD need to be recomputed upon failure, and they can be recomputed in parallel on different [nodes]." That is a fundamentally different recovery model from a courier's (replay a durable per-parcel record). ([RDD paper, NSDI'12](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf))

- **What the analogy does *not* buy a single-host Python app** — `[OPINION, grounded]` (a) There is no resource-acquisition problem to solve on one host, so a "cluster manager" layer is pure ceremony — the only real concern it addresses (which process gets which slot) is a semaphore plus a queue. (b) Spark's units are immutable partitions processed by deterministic lineage-recomputable transformations; a courier's units are mutable, side-effecting parcels whose send step is *not* recomputable for free, so nothing in the Spark model gives you dedup or at-most-once side effects. (c) Spark's cross-partition ordering is nonexistent by design, whereas per-destination ordering is your central requirement. (d) The driver is a single scheduling point that must stay network-addressable — copying that shape onto one box buys a single point of failure with no compensating parallelism. What *does* transfer is the separation of "plan/schedule" from "execute", and the practice of shipping the task (closure) rather than pulling work through a shared mutable agenda. ([spark.apache.org/docs/latest/cluster-overview.html](https://spark.apache.org/docs/latest/cluster-overview.html), [RDD paper, NSDI'12](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf))

## F. Job-scheduler prior art for "fetchers declare their own schedule"

- **Cron: field grammar and per-field jitter** — `crontab(5)` (cronie) defines the five time fields with `*`, ranges (`a-b`), lists, and steps (`*/n`, `a-b/n`); notably it also supports explicit randomization inside a field: "A random number within a range specified as two numbers separated with a tilde is picked… The random number is picked when the crontab file is [installed]" — so `~` in the minutes field yields a random minute in 0–59. ([man7.org/linux/man-pages/man5/crontab.5.html](https://man7.org/linux/man-pages/man5/crontab.5.html))

- **Interval vs. self-reported next time** — `[OPINION, mechanism-grounded]` Three distinct contracts: *interval* (next = last + Δ, drifts and piles up under load), *calendar* (next = next matching instant, needs catch-up/misfire policy), and *self-reported* (the worker returns "come back at T", which is the only one that can express "the upstream has nothing for you until T+5m"). The standardized self-reporting primitive on the web is `Retry-After`: "Servers send the 'Retry-After' header field to indicate how long the user agent ought to wait before making a follow-up request… either an HTTP-date or a number of seconds to delay after receiving the response." ([rfc-editor.org/rfc/rfc9110.html#section-10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html))

- **Jitter, two different purposes (systemd's terminology is the clearest)** — `AccuracySec=` "specifies the accuracy the timer shall elapse with. Defaults to 1min… Within this time window, the expiry time will be placed at a host-specific, randomized, but stable position… in order to optimize power consumption to suppress unnecessary CPU wake-ups." It "should not be confused with `RandomizedDelaySec=`… which adds a random value to the time the timer shall elapse next and whose purpose is the opposite: to stretch elapsing of timer events over a longer period to reduce workload spikes." If both are used, "first the randomized delay is added, and then the result is possibly further shifted to coalesce it." ([freedesktop.org/.../systemd.timer.html](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html))

- **Misfire / catch-up semantics, as a product decision** — systemd `Persistent=`: "the time when the service unit was last triggered is stored on disk. When the timer is activated, the service unit is triggered immediately if it would have been triggered at least once during the time when the timer was inactive." And the coalescing rule: "if a calendar timer elapsed more than once while the system was continuously sleeping the timer will only result in a single service activation." ([freedesktop.org/.../systemd.timer.html](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html))

- **APScheduler's `misfire_grace_time` + `coalesce` + `max_instances`** — "When this happens, the job is considered to have 'misfired'. The scheduler will then check each missed execution time against the job's `misfire_grace_time` option… to see if the execution should still be triggered. This can lead into the job being executed several times in succession." Coalescing collapses them: "if coalescing is enabled for the job and the scheduler sees one or more queued executions for the job, it will only trigger it once. No misfire events will be sent for the 'bypassed' runs." Also "by default, only one instance of each job is allowed to be run at the same time… if the job is about to be run but the previous run hasn't finished yet, then the latest run is considered a misfire" (tunable via `max_instances`), and a job can be skipped for being "run too late" when the executor pool is saturated. ([apscheduler.readthedocs.io/en/3.x/userguide.html](https://apscheduler.readthedocs.io/en/3.x/userguide.html))

- **Exponential backoff with jitter (the canonical AWS treatment)** — Capped exponential backoff still produces synchronized clusters of retries ("we've just introduced times when no client is competing"); adding jitter spreads them to "an approximately constant rate of calls," and with 100 contending clients "we've reduced our call count by more than half." The three named variants are **Full Jitter** (`sleep = random(0, min(cap, base·2^attempt))`), **Equal Jitter** (keep half the backoff, jitter the other half), and **Decorrelated Jitter**, which "is similar to 'Full Jitter', but we also increase the maximum jitter based on the last random value" (`sleep = min(cap, random(base, previous_sleep·3))`). Their verdict: no-jitter is "the clear loser"; Equal Jitter "does slightly more work than Full Jitter, and takes much longer"; Full vs Decorrelated is a work-vs-time trade-off. Note the honest caveat: none of them "fundamentally change the N² nature of the work to be done." ([aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/))

- **Token bucket** — Stripe's implementation: "a centralized bucket host where you take tokens on each request, and slowly drip more tokens into the bucket. If the bucket is empty, reject the request. In our case, every Stripe user has a bucket, and every time they make a request we remove a token from that bucket," backed by Redis, with the operational rule that the limiter must "fail open" if Redis or the limiter code breaks. ([stripe.com/blog/rate-limiters](https://stripe.com/blog/rate-limiters))

- **Leaky bucket vs GCRA** — Leaky bucket: fixed capacity τ, constant drain rate, cost-proportional inflow, "actions are disallowed if the bucket is full" — hence a smooth output but it "is normally implemented using a background process that simulates a leak," whose weakness is that a failed drip process causes incorrect limiting. GCRA removes the drip: it tracks a "theoretical arrival time" (TAT), seeded on first request by adding the cost; on each request it takes TAT, subtracts the burst buffer (τ + T), compares with now — past ⇒ allow, future ⇒ reject — and on success advances TAT by the emission interval T. So burst capacity and sustained rate are two independent parameters and state is a single timestamp per key. ([brandur.org/rate-limiting](https://brandur.org/rate-limiting))

- **Hierarchical/hashed timing wheels vs heaps** — Varghese & Lauck: conventional timer implementations "take O(n) time to start or maintain a timer, where n is the number of outstanding timers"; a timing wheel over a circular buffer gives "O(1) time to start, stop, and maintain timers within the range of the wheel," with two extensions for long intervals — hashing the interval into a wheel slot, and a hierarchy of wheels with different granularities. The design point for a courier: a single global heap is O(log n) per operation but re-prioritises on every insert, while wheels give O(1) *if* you accept granularity (the wheel's tick) as the accuracy floor. ([Hashed and Hierarchical Timing Wheels, SOSP'87](https://www.cs.columbia.edu/~nahum/w6998/papers/sosp87-timing-wheels.pdf))

- **Why "sleep until T" is the wrong scheduler primitive in a broker** — `[FACT, from RabbitMQ docs]` TTL-based delay inherits head-of-queue expiry ("expired messages can queue up behind non-expired ones"), and the delayed-message plugin loses messages on node loss. `[OPINION]` Therefore schedule as *data* (a `next_attempt_at` column / `x-opt-delivery-time` header) and let a poller do a range scan, rather than as an in-memory timer per parcel. ([rabbitmq.com/docs/ttl](https://www.rabbitmq.com/docs/ttl), [rabbitmq-delayed-message-exchange README](https://github.com/rabbitmq/rabbitmq-delayed-message-exchange))

## G. Durable execution / workflow engines

- **Temporal: event history + deterministic replay** — A workflow execution "emits a series of Commands and processes a sequence of Events, which are recorded in an Event History"; on resume Temporal "doesn't restore memory from a snapshot. It starts the Workflow code from the beginning, replays the Event History step by step, and uses that history to guide the code back to the exact state as before." Consequence: the code must be deterministic w.r.t. history — `Date.now()`, randomness, and un-journaled network calls are provided as replay-safe APIs, and side effects belong in Activities. ([docs.temporal.io/workflows](https://docs.temporal.io/workflows))

- **Temporal: signals vs queries vs updates, and timers as commands** — "Queries are read requests… Signals are asynchronous write requests. They cause changes in the running Workflow, but you cannot await any response or error. Updates are synchronous, tracked write requests." Progress may only block on SDK-provided Awaitables, one of which is "Starting a Timer: Progress can block until the Timer fires" — i.e. a durable timer is a command whose firing is an event in history, not a process sleep. ([docs.temporal.io/encyclopedia/workflow-message-passing](https://docs.temporal.io/encyclopedia/workflow-message-passing), [docs.temporal.io/workflow-execution](https://docs.temporal.io/workflow-execution))

- **DBOS: checkpoints in Postgres, no orchestration server** — "You use DBOS by installing the open-source library into your application and annotating workflows and steps. While your application runs, DBOS checkpoints those workflows and steps to a Postgres database… it uses those checkpoints to recover each of your workflows from the last completed step." `DBOS.sleep()` is durable — "DBOS saves the wakeup time in the database so that even if the workflow is interrupted and restarted multiple times while sleeping, it still wakes up on schedule" — and `DBOS.recv` is the durable receive counterpart. "There's no separate orchestration server and no infrastructure required besides Postgres." ([docs.dbos.dev/architecture](https://docs.dbos.dev/architecture), [docs.dbos.dev/python/tutorials/workflow-tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial))

- **Restate: journal + invocation identity + durable delayed sends** — "Restate tracks every step of your code execution in a journal. When you call other services, update databases, set timers, or perform any side-effecting operation, Restate records both the operation and its result. If your function crashes or fails, Restate replays the journal, skipping completed steps and resuming from exactly where it left off." Invocation identity is the dedup mechanism: "an invocation represents a request to execute a handler. Restate tracks each invocation through completion, ensuring it runs exactly once regardless of failures," and "if you add an idempotency key to your request headers, Restate will automatically ensure that requests are deduplicated." Delayed work is a one-way call with a `delay` option. ([docs.restate.dev/foundations/key-concepts](https://docs.restate.dev/foundations/key-concepts), [docs.restate.dev/foundations/actions](https://docs.restate.dev/foundations/actions))

- **Why this matters for "a relay station re-enters the pipeline"** — `[OPINION, grounded in the above]` A relay that parks a parcel and re-injects it later is exactly a durable state machine with (a) a persisted position, (b) timers that survive restarts, and (c) stable identity for the resumed unit of work. All three engines converge on the same two primitives — an append-only journal keyed by a stable invocation id, and timers-as-events — which is the design to copy even in a small custom implementation. The engines differ mainly in *where* the journal lives (Temporal service / Postgres / Restate server) and whether you write plain code (DBOS, Restate) or workflow-deterministic code (Temporal). ([docs.temporal.io/workflows](https://docs.temporal.io/workflows), [docs.dbos.dev/architecture](https://docs.dbos.dev/architecture), [docs.restate.dev/foundations/key-concepts](https://docs.restate.dev/foundations/key-concepts))

## H. Delivery-guarantee theory

- **The three semantics, defined by a messaging vendor's own doc** — "at-most-once delivery means that for each message handed to the mechanism, that message is delivered once or not at all… at-least-once delivery means that for each message handed to the mechanism potentially multiple attempts are made at delivering it, such that at least one succeeds… exactly-once delivery means that for each message handed to the mechanism exactly one delivery is made to the recipient; the message can neither be lost nor duplicated." Cost ordering is stated explicitly: at-most-once is cheapest (no sender state), at-least-once needs retries + state + acks, exactly-once "is most expensive… because in addition to the second it requires state to be kept at the receiving end in order to filter out duplicate deliveries." ([doc.akka.io/.../general/message-delivery-reliability.html](https://doc.akka.io/libraries/akka-core/current/general/message-delivery-reliability.html))

- **Why exactly-once (as *delivery*) is impossible** — Two Generals / FLP: after a lost ack you cannot distinguish "not delivered" from "delivered, ack lost," so any retry can duplicate and any non-retry can lose. "Every major message queue in existence which provides any guarantees will market itself as at-least-once delivery. If it claims exactly-once, it's because they are lying to your face." The practical resolution: "the messages themselves should be idempotent… or we remove the need for idempotency through deduplication," ideally with commutative, order-independent operations. ([bravenewgeek.com/you-cannot-have-exactly-once-delivery](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/))

- **"Effectively-once" is the honest name** — It is a property of (transport at-least-once) + (receiver-side dedup or idempotent effect), not of the transport. `[FACT]` Kafka says the same thing structurally: broker-side idempotence only dedups *resends within a producer session* (producer id + sequence number), and end-to-end exactly-once "for other destination systems generally requires cooperation with such systems." ([kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design))

- **Idempotency keys: the standardized contract** — "An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request." The key "MUST be unique and MUST NOT be reused with another request with a different request payload"; the resource "MUST publish an idempotency-related specification… [and] SHOULD define such expiration policy." Enforcement distinguishes first request (process normally), duplicate-after-completion (respond consistently with the original outcome), and duplicate-concurrent (respond with a conflict error), optionally strengthened by a payload-derived *idempotency fingerprint*. ([draft-ietf-httpapi-idempotency-key-header-08](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/))

- **Dedup windows are a capacity/licensing decision, not a correctness one** — `[FACT]` The draft requires the resource to publish an expiry policy for keys, which means dedup is only guaranteed inside that window; `[OPINION]` therefore the window must be sized against the maximum plausible retry horizon (max retry backoff × attempt budget + max queue dwell), and anything outside it must be caught by an idempotent effect at the destination rather than by the dedup table.

- **Why "ordered + at-least-once + multi-consumer" is in tension** — `[FACT]` Each pair conflicts in a documented way: (1) *at-least-once + ordering*: any redelivery reorders, because the redelivered item re-enters at a different position — RabbitMQ states exactly this for shared queues; (2) *ordering + multiple consumers*: two consumers processing consecutive messages concurrently destroys the order, which is why SAC exists and why Sequential Convoy partitions by key; (3) *at-least-once + multi-consumer + one logical stream*: retries and parallelism both require a resequencer with a timeout, and the timeout is the point where you must choose between "emit out of order" and "stall the convoy." ([rabbitmq.com/docs/queues](https://www.rabbitmq.com/docs/queues), [learn.microsoft.com/.../sequential-convoy](https://learn.microsoft.com/en-us/azure/architecture/patterns/sequential-convoy), [camel.apache.org/.../resequence-eip.html](https://camel.apache.org/components/latest/eips/resequence-eip.html))

## WHAT THIS IMPLIES FOR A 4-STAGE PIPELINE (fetch → parse → render → send) WITH PER-DESTINATION ORDERING

Assumptions: single host initially, per-destination ordering required, stages are relay/terminal stations, dead-letter handling required, "fetchers declare their own schedule."

**1. Where the ordering boundary lives.**
- `[FACT]` Every ordering primitive surveyed is *per key on one queue/partition* — RabbitMQ FIFO per queue with reordering on redelivery or shared consumers, Kafka per-partition, Sequential Convoy per session, Akka per sender–receiver pair, Spark nowhere. There is no "pipeline order" to inherit; you must create it. ([rabbitmq.com/docs/queues](https://www.rabbitmq.com/docs/queues), [kafka.apache.org/documentation/#design](https://kafka.apache.org/documentation/#design), [learn.microsoft.com/.../sequential-convoy](https://learn.microsoft.com/en-us/azure/architecture/patterns/sequential-convoy))
- `[OPINION]` Put the ordering boundary at the **narrowest point with a real causal dependency: (destination × send-order-key) at the terminal station**, not at fetch. Fetch/parse/render are naturally parallel and keyless; ordering them buys nothing and costs everything (you would serialise unrelated destinations behind one slow fetch). Send is where the external world observes order (messages in a thread, edits to a page), so serialize there.
- `[OPINION]` Concretely: one in-flight parcel per destination (a convoy of width 1 per destination), plus a per-destination monotonic sequence number on every parcel so the terminal station can detect gaps rather than trusting arrival order — the exact recipe the Sequential Convoy page gives for out-of-order arrival before broker ordering applies. ([learn.microsoft.com/.../sequential-convoy](https://learn.microsoft.com/en-us/azure/architecture/patterns/sequential-convoy))
- `[OPINION]` Do **not** implement "one consumer per destination" with a shared queue. Per the RabbitMQ doc, multiple active consumers on one queue keep FIFO dequeue but "any redelivery can change order"; your retry path *is* a redelivery, so the guarantee evaporates exactly when you need it. Use single-active-consumer semantics or `x-modulus-hash`/`x-consistent-hash` partitioning so the ordering unit is a physical queue, and remember consistent hashing re-routes keys when the queue count changes. ([rabbitmq.com/docs/queues](https://www.rabbitmq.com/docs/queues), [rabbitmq consistent-hash README](https://github.com/rabbitmq/rabbitmq-server/blob/main/deps/rabbitmq_consistent_hash_exchange/README.md))

**2. Where dedup belongs.**
- `[FACT]` Dedup is only ever receiver-side and only ever within a window; the transport cannot supply it end-to-end. ([draft-ietf-httpapi-idempotency-key-header-08](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/), [bravenewgeek.com/you-cannot-have-exactly-once-delivery](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/))
- `[OPINION]` Dedup belongs **at the terminal station, immediately before the irreversible side effect**, keyed by a stable `idempotency_key = hash(parcel_id, destination, stage="send")` that is *derived, not regenerated* on retry — the IETF draft's rule that a key must never be reused with a different payload is the whole game. Relay stations must be *idempotent by construction* (pure functions of the parcel body + stage inputs, writing outputs under the same key) rather than dedup-checked; that is the Idempotent Receiver pattern's second route, "defining the message semantics to support idempotency," and it is much cheaper than a dedup table per station. ([IdempotentReceiver.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/IdempotentReceiver.html), [draft-ietf-httpapi-idempotency-key-header-08](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/))
- `[OPINION]` Size the dedup window explicitly and publish it, then stop pretending: anything older than the window must be caught by the destination's own idempotency (e.g. the provider's idempotency key on the send API), not by your table.

**3. Where retry/backoff belongs.**
- `[FACT]` Requeue-in-place is not a retry mechanism: RabbitMQ republishes at/near the original queue position and requeued messages "may be immediately ready for redelivery," producing hot redelivery loops; and `basic.nack`-requeue no longer even counts toward a quorum queue's delivery limit, so it can loop forever. ([rabbitmq.com/docs/confirms](https://www.rabbitmq.com/docs/confirms), [rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))
- `[OPINION]` Retry belongs to **the station that failed, expressed as data, not as a sleep**: persist `attempt_count` and `next_attempt_at` alongside the parcel, and let a scheduler re-admit it. That is RabbitMQ's own recommended path ("quorum queues natively support delayed retry… supports linear back-off per queue and explicit per-message delivery times," `delay = min(min_delay*delivery_count, max_delay)`), and it is the only form that survives process death. ([rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))
- `[OPINION]` Backoff must be jittered, and the jitter must be *decorrelated* or *full*, not equal-jitter, because your failure mode is many destinations retrying against the same upstream simultaneously — precisely the contended-clients case in the AWS post. ([aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/))
- `[OPINION]` Retry bubbles in one direction only, and hops are bounded: per-stage attempt budgets, and a hard total budget for the parcel. The moment a retry re-enters *before* a stage that already produced a side effect, you have manufactured a duplicate — this is the structural reason "relay station re-enters the pipeline" must re-enter *at its own stage*, carrying its accumulated state, not at stage 1.

**4. Itinerary as data (routing slip) vs code (process manager).**
- `[FACT]` Routing Slip presumes the step list is decided up-front and linear and is carried in the message; Process Manager exists for when the next step depends on intermediate results, and centralises state at the cost of a hub bottleneck. ([RoutingTable.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RoutingTable.html), [ProcessManager.html](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html))
- `[OPINION]` For a fixed 4-stage fetch→parse→render→send pipeline, **the itinerary should be data**: the stage list is known at admission, it survives crashes with zero coordinator, every station can be restart-independent, and the delivery mechanism (header/property, as Camel does with `CamelSlipEndpoint`) is trivially inspectable in a dead-letter record. Write the slip as an explicit ordered array with a cursor, not as "which stage am I in" derived from mutable status.
- `[OPINION]` What must **not** be in the slip: retry policy, timeouts, concurrency limits, destination routing rules. Those are policy and belong in a table the stations read (a small process manager *for policy*, not for position) — otherwise every slip edit becomes a data migration for in-flight parcels. This is the practical split: **slip = where the parcel goes; process manager-ish config = how a station behaves.**
- `[OPINION]` If a stage ever needs to skip/repeat/reorder based on a result (e.g. render says "content too long, re-parse"), that is the trigger to move to a Process Manager, not to teach the slip to rewrite itself — self-modifying itineraries are unreviewable and break replay determinism, which is exactly what every durable-execution engine forbids. ([docs.temporal.io/workflows](https://docs.temporal.io/workflows))

**5. Where the dead-letter station must sit.**
- `[FACT]` Dead-lettering is a per-queue/station decision, carries provenance (`x-death` with `queue`, `reason`, `count`, `first-time`/`time`), is at-most-once by default unless the target is a quorum queue, and can silently loop unless cycles are detected. ([rabbitmq.com/docs/dlx](https://www.rabbitmq.com/docs/dlx))
- `[OPINION]` Three distinct parking areas, not one:
  1. **Per-stage DLQ** for anything that exhausts that stage's budget, carrying `stage`, `attempt_count`, `last_error`, and the slip cursor. Provenance is not optional — without `{stage, reason, count}` you cannot tell "parse is broken" from "this destination is gone."
  2. **A pre-send "hold" area** for parcels that are valid but must not be sent yet (missing predecessor, destination paused). This is *not* a dead letter — it is the deferred/claim mechanism, and conflating it with the DLQ is how you end up replaying good parcels as failures. RabbitMQ's 4.4 deferral with `x-opt-deferral-token` is the closest broker primitive; a `next_attempt_at` + `blocked_on` column is the equivalent at app level. ([rabbitmq.com/docs/quorum-queues](https://www.rabbitmq.com/docs/quorum-queues))
  3. **A terminal DLQ after send** only for the case "we sent it and cannot confirm" — the genuinely ambiguous one, which must be resolved by the destination's idempotency key, not by guessing.
- `[OPINION]` The DLQ must sit *before* the irreversible effect and *after* the last retryable step: a parcel that fails in fetch/parse/render may be retried or discarded freely; a parcel that fails in send may already have landed. So the send station's DLQ must record the outbound idempotency key it used, or the DLQ is unreplayable.
- `[OPINION]` A poison parcel in a per-destination convoy blocks the whole convoy (documented on the Sequential Convoy page), so per-stage attempt budgets are not a nicety — they are the mechanism that protects destination D's later parcels from destination D's earlier bad one.

**6. Fetchers declaring their own schedule.**
- `[OPINION]` Accept self-reported `next_poll_at`, but treat it as advisory and clamp it: `next = clamp(reported, now + min_interval, now + max_interval)` with jitter, because a fetcher that reports "never" or "in 10 years" starves its destination, and a fetcher fleet reporting the same instant reproduces the thundering-herd the AWS post describes. Persist `next_poll_at` in the same store as the parcels so a restart does not lose the schedule — the `Persistent=` lesson from systemd, where catch-up-on-missed-run is an explicit, separately-switchable policy. ([freedesktop.org/.../systemd.timer.html](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html), [aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/))
- `[OPINION]` Choose coalescing explicitly rather than by accident: if a fetcher misses 25 windows, running it 25 times is almost never right (APScheduler's `coalesce`), and `Retry-After`/`next_poll_at` in the past should mean "run once, now," not "run N times." ([apscheduler.readthedocs.io/en/3.x/userguide.html](https://apscheduler.readthedocs.io/en/3.x/userguide.html), [rfc-editor.org/rfc/rfc9110.html#section-10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html))
