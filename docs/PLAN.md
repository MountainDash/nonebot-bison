# 实施计划

依据：[设计规格](specs/README.md)、[词汇表](../GLOSSARY.md)、[ADR](adr/)。

## 全局规则

前五次 courier 尝试的死法是同一个：**一次吃掉全部，写一天，推上去，停**。五条规则直接针对它：

1. **每个里程碑结束时系统必须是能跑的。** 没有「中间态不可运行」的里程碑。
2. **每个里程碑结束时必须 commit + tag + 可运行 + 测试通过。** 里程碑之间的工作区不留给下一个人。
3. **任一里程碑不超过 1.5 周。** 超过就说明它该拆，不是说明它难。
4. **不引入未被规格要求的依赖。** 规格里写了 `anyio` + `sqlalchemy`(Core) + `pydantic`，就这些。
5. **里程碑顺序是依赖顺序，不是优先级。** 想提前做 M6 的人必须先想清楚为什么 M3 已经不需要它。
6. **每个里程碑拆成一个链式 PR 栈**（见下节）。栈内一个 PR 只做一件事，≤ 400 行（不含测试与生成物），合并后主干测试全绿。
7. **测试与实现在同一个 PR 里。** 不允许「先实现、后补测试」，也不允许「最后来一个测试 PR 收口」—— 后者正是「写一天、推上去」的形状。

## PR 切片

### 栈与链

**一个里程碑 = 一个栈。** 栈内 PR 逐层相接：每一层的 base 是下一层的分支，栈底指向 `main`。栈底合并后，下一层自动改指向 `main`（GitHub 的 stacked PRs 就是这个模型；未开启预览时用 `gh pr create --base <下一层分支>` 得到同样效果）。

**为什么不是一条 38 层的长链：**

- review 疲劳。一次看 38 个 PR 和看 6 个是两回事，而栈的价值就在于「一层一层往上 review」。
- rebase 成本。栈底任何改动都要向上级联 38 次。
- **最重要的是停损形状。** 按里程碑分栈，最坏情况是停在某个栈的中间，而它的**栈底已经合进 main**，主干永远是好的。若是一条长链，停在中间会留下几十层未合并的分支 —— 那正是五次失败的形状，只是换了个名字。

**合栈时机：** 栈内每层各自 review 与合并；整个栈在里程碑验收通过后合完并打 tag（`m0`…`m6`）。

### 判据

一个改动够格成为一个 PR，当且仅当它能在**不读其他 PR 的情况下被单独 review**，且满足：

- **一个理由**：标题能写成一句「为了 X 而 Y」，不需要「顺便」。
- **≤ 400 行**（不含测试、fixture、生成物）。超了就说明它包含两个理由。
- **主干保持可运行**：合并后 `uv run pytest` 全绿；M3 之后还要求 bison 能启动。
- **行为变化必带测试**：courier 的每个 PR 至少新增或修改一个行为测试。
- **决策变化必带文档**：若 PR 改变了已记录的决策，ADR / GLOSSARY 在**同一个 PR** 里更新。

M3 之前「可运行」只要求 workspace 测试全绿（此时还没有产品）；M3 之后要求 bot 能启动。未接线的代码以「已实现但未注册」的方式进入主干，不影响运行 —— 这是让垂直切片可以分批合并且不怕中途停下的关键。

### PR 检查清单

每个 PR 描述里必须有：

- [ ] 一行「为什么」：为了 X 而 Y
- [ ] 一行「怎么验证」：跑哪个测试 / 点哪个界面
- [ ] 是否改变已发布的接口？（改了就说明有兼容问题）
- [ ] 是否改变已记录的决策？（改了就在同一 PR 更新 ADR / GLOSSARY）
- [ ] diff 是否 ≤ 400 行（不含测试）

## 里程碑

### M0 — 工程地基（2–3 天）

**产出**

- uv workspace：`packages/courier`、`packages/bison`，各自 `pyproject.toml`。
- `courier` 的 DI 模块：以 [courier_di.py](research/prior-art/courier_di.py) 为起点，补上「provider 自身依赖在 `register()` 期递归校验」。
- `Store` Protocol 定义（先只有签名）。
- CI：`ruff` + `pytest`。

**验收**

- `uv run pytest` 全绿。
- **一个测试断言 `import courier` 之后 `sys.modules` 里没有 `nonebot`** —— 这是 ADR 0001 唯一的机械保证。
- DI 的四个行为测试：singleton、marker 键、重复注册报错、缺 provider 在装饰期炸。

---

### M1 — courier 内核闭环（内存 Store，3–5 天）

**产出**

- `Parcel` / `Receipt`：全部字段可 `json` 往返（有一条专门的往返测试）。
- `register()` / `post()` / `post_many()`（原子性先用内存事务模拟）。
- 单 worker 循环 + `post()` 唤醒。
- 重试（3 次 / 5s / 30s / 2min，可注入时钟）、死信兜底站点、循环检测、后代预算。
- 内存 `Store`。

**验收（语义测试，全部无数据库）**

1. **顺序**：同一信道上 A、B、C 三个包裹按序完成，且 A 未结算时 B 不被取出。
2. **隔离**：信道 X 的包裹连续失败时，信道 Y 的包裹照常完成。
3. **重试**：失败包裹在原信道重试，退避时间符合预期（注入时钟断言）。
4. **死信**：重试耗尽进回收站，带上 `attempt_count` / `last_error` / `last_error_kind`。
5. **回收站不自噬**：回收站站点抛异常时只记日志，不产生新的死信。
6. **扇出**：一个站点返回 20 个包裹，全部入队。
7. **扇出原子性**：扇出的第 7 个包裹写入失败时，前 6 个也不可见。
8. **子包裹幂等**：同一个父包裹重跑扇出，子包裹不重复。
9. **循环**：`A → B → A` 被拦下，进回收站（`routing`）。
10. **预算**：后代超过上限进回收站（`fanout_exceeded`）。

**停损条件**：第 1 或第 2 条写不出来，说明 [ADR 0002](adr/0002-channel-is-a-logical-lane.md) 有洞，**停下来改设计，不要绕过去写 bison**。

---

### M2 — 持久化（3–4 天）

**产出**

- 三张表：`parcels`、`lanes`、`dead_letters`（+ 索引）。
- `Store` 的 SQLAlchemy Core 实现，`AsyncEngine` 注入。
- 库的初始化/迁移路径（先手写 DDL + 版本表即可，暂不引 Alembic）。
- 一个崩溃注入测试工具。

**验收**

- M1 的十条语义测试全部改跑在 SQLite 上，仍然全绿。
- **崩溃恢复**：在「扇出写了一半」处强杀进程 → 重启后要么全在要么全不在，且不重复。
- **重启续跑**：一个 `next_attempt_at` 在未来的包裹，重启后到点仍被取出。
- **HTTP 无关**：`Store` 实现里没有任何 `nonebot` 引用。

---

### M3 — 垂直切片：一个抓取器 → 一个目的地（5–7 天）

这是整条路的证据。它跑通之前，任何扩功能都是赌博。

**产出**

- bison 最小骨架：`Component` 基类、通用适配器、注册中心（内存版）。
- 一个**真**抓取器：**RSS**（无凭证、无风控、最好测）。
- 内建直通解析器 + `basic` 渲染器 + SAA 发送器。
- 最小数据模型：`source` / `destination` / `subscription`。
- NoneBot 接线：`on_startup` 校验并 `courier.run()`，`on_shutdown` 排干。
- `inspect()` 数据结构定稿（网页什么时候做都不影响它）。

**验收**

1. 在真 NoneBot 里跑起来，一个 RSS 源 → 一个群，端到端收到消息（用 `nonebug` 或真适配器）。
2. **重启不重复**：投递后重启，不重发。
3. **停机不丢**：停机 30 分钟后重启，期间的更新被补发（受 24h / 200 条上限约束）。
4. **单个目的地卡住不影响另一个**：两个群，一个故意配置成错误 id，另一个正常。
5. **缺注册拒绝启动**：删掉发送器后启动失败，报错列出全部缺失项。

**到此为止系统的状态**：能替代旧 bison 的最小可用形态。后面每一步都是加法。

---

### M4 — 组件生态与配置（5–7 天）

**产出**

- 配置系统：组件声明 pydantic schema、loader 组装、三层覆盖、报错定位到「哪个组件哪一段」。
- `external` 组件的升格机制（解析器/富化器声明 external → 独立站点 + 自己的资源键）。
- 富化器（`adds` / `required` + 四条启动校验）。
- 专线包骨架：`bison_api_version` 声明与启动期校验。
- 装配规则：按类型配对、冲突报错、发送器按目的地 `sender` 字段。

**验收**

- 第二个抓取器作为**独立专线包**接入，**不改核心代码**。
- 配置里写一个不存在的组件名 → 启动失败并指出位置。
- 一个 `external=True` 的富化器（可先用假的外部 API）拥有独立的重试预算与资源键。
- 一个 `adds` 冲突的富化器组合 → 启动失败。

---

### M5 — 迁移（4–6 天）

**产出**

- `bison-migrate`：`nb bison-migrate` 子命令 + `python -m bison_migrate`，同一份代码。
- 两场迁移：旧 6 张表 → 新 schema；datastore SQLite → orm。
- 检测：`nonebot_bison_` 前缀 + 迁移标记行；新 bison 启动前置检查。
- `--dry-run`、可重跑、**绝不删旧表**。
- 首轮静默初始化 + 「已接管 N 条订阅」告知。

**验收**

- 用一份真实旧库跑迁移，订阅数 / 目的地 / 凭证逐项对上。
- 迁移中途 kill → 重跑成功且不重复。
- 未迁移时启动新 bison → 拒绝启动并提示。
- 旧库文件在迁移后**逐字节未变**。

---

### M6 — 网页与可观测（5–8 天）

**产出**

- Prometheus 指标：`channel_head_age_seconds`、`dead_letter_count{reason_kind}`、`fetch_outcome`、`enricher_failures`、`render_duration`、`degradation_count`。
- 死信主动通知管理员。
- 网页：同进程挂载、复用 JWT、**重写 API**、写操作白名单（重试死信 / 暂停订阅 / 刷新源名字）。
- 前端先审计旧 SPA 再决定改造程度。

**验收**

- 网页能看到信道积压、死信、组件依赖与配置 schema、源名字与降级计数。
- 三个白名单写操作可用，其余全部 403。
- 死信产生后管理员收到通知。

---

## 依赖关系

```
M0 ──> M1 ──> M2 ──> M3 ──> M4 ──> M5
                       └──> M6（可在 M4 之后并行）
```

M3 之前**不得**开始 M4/M5/M6 的任何代码。原因不是优先级，是：M3 之前 bison 的组件形状还不存在，配置系统与网页都没有可作用的对象。

## 明确不做

| 不做 | 原因 |
|---|---|
| 多进程 / 分布式运输器 | 规格的非目标；接口形状已留口子 |
| Alembic（M2 之前） | 先手写 DDL，表稳定后再引 |
| 旧 admin 的 API 形状 | 16 条路由全绑旧模型 |
| entry points 发现子包 | 会是第二套发现机制 |
| 多源类型齐上 | M3 只做 RSS，跑通再扩 |
| 任何以吞吐为由的优化 | 500 条/天，见规格的约束基线 |

## 风险与停损

| 风险 | 停损条件 |
|---|---|
| 信道语义写不出来（M1） | 第 1、2 条验收不过 → 回改 ADR 0002，不动 bison |
| 持久化后语义漂移（M2） | M1 测试在 SQLite 上有任何一条变红 → 不进入 M3 |
| 组件形状不够用（M3） | 第二个抓取器需要改核心才能接入 → 停，重看「站点边界判据」 |
| 迁移数据对不上（M5） | 任一项对不上 → 不发布，继续在 `--dry-run` 里修 |
| 又开始大爆炸 | 任一里程碑超过 1.5 周 → 强制拆分，不例外 |

## 完成定义

同时满足以下四条才算这个项目「做完了」：

1. 旧 bison 的一个真实部署能迁移过来并跑满一周，无漏发、无重复、无人工干预。
2. 第三方能写一个专线包接入，不需要读 courier 的源码。
3. 一个目的地坏掉不会影响其它目的地，且管理员能收到通知。
4. 重启与断电不会造成静默漏发。
