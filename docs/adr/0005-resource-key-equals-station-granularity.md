# 信道按资源划分，资源粒度等于站点粒度

信道键是一个不透明的**资源**字符串，由站点声明。规则是：**一个站点的资源画像就是它的风控画像 —— 需要两个画像就拆成两个站点。**

抓取器的资源键形如 `host#凭证`，发送器的资源键就是目的地。courier 不解释这个字符串，只用它决定「谁和谁共享一条信道」，因此共享同一凭证的两个源会自动共享节流与风控退避，而换凭证即换信道，旧凭证的退避不会拖累新凭证。

## Considered Options

- **内置「凭证」概念**：courier 会因此需要理解 cookie、轮换、冷却 —— 业务知识渗进内核。
- **多资源门控**（一个站点声明多个资源，调度时同时获取）：更精确，但需要锁序或原子多键获取，而当前 10 个源、4–6 个 host 的规模不支持这份复杂度。
- **抓取侧不设信道、只用一个全局令牌桶**：一个源被风控会拖慢全部源。

## Consequences

- 资源键是**必需参数**。站点答不上「我和谁共享队列」，说明它的并发约束还没想清楚。
- 资源键必须**从包裹内容算出**，不能是构造函数里的常量 —— 否则换凭证不会换信道。
- **一条信道可以承载多个地址的包裹**：同凭证下的两个源落在同一信道，包裹交替出现，各自由自己的站点处理。实现不能假设「信道 ↔ 地址」一一对应。
- 答案答错有两个方向的症状：太粗 → 无关的源互相拖慢（5s 的直播轮询器给 60s 的动态轮询器定节奏）；太细 → 同一凭证被并发猛打，正好触发风控。
- 多资源门控是明确的**非目标**。B 站的三个 host 风控画像不同这件事，用「拆站点」解决（`bilibili` / `bilibili-live` / `bilibili-bangumi` 本来就是三个类），而不是用「一个站点多个资源」解决。
