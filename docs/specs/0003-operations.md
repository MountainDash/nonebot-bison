# 运行 — 进程、网页、可观测、迁移、容量

## 1. 进程与启动顺序

**单进程，courier 当前单 worker。** NoneBot 的 asyncio loop 承载对话、网页、bison 组合调度器与唯一站点 worker。

```text
加载全部插件与专线
→ 收集注册、解析配置、校验自然身份与组件装配
→ 为每个 Source 编译执行计划
→ 一次性列出全部缺失项，失败则拒绝启动
→ 提交中断恢复事务：遗留 side-effecting 执行标记转为 outcome_unknown
→ bison 启动唯一的 Source + Channel 组合调度器
→ 注册表冻结
```

插件加载顺序不确定，因此必须在加载完后统一校验。冻结只禁止运行时动态注册，不影响启动前安装与加载子包。

启动中途失败时，按创建的相反顺序释放已经建立的 Renderer、HTTP client、Sender client、调度任务与数据库资源。

## 2. 关闭与资源所有权

固定关闭顺序：

```text
停止 Source 生产，closing 后拒绝 post / 重投
→ courier 停止取新 head
→ 等待在途站点，超时后 cancel-and-await
→ 等唯一 worker 真正退出
→ 关闭各组件拥有的资源
→ 最后关闭数据库 engine
```

`close()` 幂等。默认排干等待 10 秒只是等待上限，不意味着可以留下 detached 任务。组件必须响应取消并清理自己拥有的资源；通用流水线不识别这些资源的具体类型。

未结算包裹留在存储中，重启继续。外部发送已经发生而本地未结算的关闭窗口仍可能重发，属于已声明的 at-least-once 例外。

## 3. 交付口径、SLO 与耐久部署档案

### 3.1 交付口径

系统承诺**带显式例外的 at-least-once**：

- 不得出现未报告的损失。
- 外部平台可能已接受、但本地结果不可知时允许重复，包括响应超时、断连与发送后本地结算前崩溃；必须保留 `outcome_unknown` 审计。
- `DROPPED`、`CANCELLED`、迁移截断与补抓缺口分别可见，不能混为成功或故障死信。
- 「正常关闭后不重放」「结算提交前后」「发送超时/断连」「外部发送后未结算」分别测试，不使用无故障点定义的「重启不重复」。

### 3.2 延迟口径

`p95 < 90 秒`只统计在线、非暂停、非补发、首次尝试即成功投递的内容，起点为抓取开始，终点为首个发送确认。

重试、补抓、暂停、积压、降级与关闭排干分别统计，不混入该 SLO，也不得无指标。500 条/天只是规模基线，不是延迟证据。

### 3.3 存储耐久契约与 SQLite 档案

courier 的跨后端契约是：结算原子、已提交状态在存储承诺的耐久边界内可恢复、重启后父子状态不分叉。

当前 SQLite 部署档案使用：

- WAL；
- `synchronous=FULL`；
- 有限 busy timeout；
- 不在事务内执行网络、渲染或文件等待的短事务。

这些是 SQLite 配置，不是 `Store` Protocol 的永久要求。更换 Store 时必须提供等价或明确不同的耐久档案，并重新执行崩溃矩阵。

M2 的进程强杀测试证明进程崩溃原子性；已提交事务的断电耐久在 SQLite `FULL` 保证范围内描述，不能声称一次 kill 测试覆盖了所有操作系统与硬件故障。

## 4. 网页、权限与 secret

网页同进程挂载，复用 JWT 身份，但**重新实现对象级授权**。写白名单只决定允许哪些动作，不决定允许对哪些对象执行。

### 4.1 权限矩阵

| 动作/数据 | 目的地管理员 | 超管 |
|---|---:|---:|
| 查看自己目的地的订阅、降级与丢弃 | ✓ | ✓ |
| 暂停/恢复自己目的地的订阅 | ✓ | ✓ |
| 查看并重投与自己目的地直接相关的发送死信 | ✓ | ✓ |
| 共享抓取/解析死信、全局 channels/components/resources | — | ✓ |
| 刷新共享 Source 名字 | — | ✓ |
| 重投共享上游死信 | — | ✓ |

每次请求都根据目标对象重新鉴权；未授权对象按不可见处理并记录安全审计。正常读取按范围开放，非白名单写操作拒绝；不能用「其余全部 403」替代逐路由验收。

允许的写动作只有：重投一条死信、暂停/恢复一条订阅、刷新源名字。重投是条件状态迁移，重复请求返回同一新投递代。

### 4.2 secret 边界

凭证 id 随机且不透明。secret 不进入 resource、inspect、配置快照、指标、日志、异常、死信上下文或 dry-run 报告；迁移校验只比较安全摘要或计数，不打印原值。

首版明确把数据库文件及其备份列为高敏边界：能读取文件就能读取凭证，必须由操作系统权限保护。若将来要求静态加密，需要另行决定密钥来源、轮换与新增依赖，不能顺手引入。

## 5. 可观测与告警

指标由 bison 暴露，courier 只提供通用状态与事件。最小集合包括：

| 指标 | 用途 |
|---|---|
| `channel_head_age_seconds{resource}` | 当前 head 积压；暂停单独标注 |
| `dead_letter_count{reason_kind}` | 自动运输失败 |
| `fetch_outcome{source, result}` | 抓取与风控 |
| `send_outcome{destination, result}` | 发送成功、确定失败、重试与 `outcome_unknown` |
| `delivery_latency_seconds` | §3.2 条件口径的端到端延迟 |
| `enricher_failures{enricher}` | 可选与必需富化失败 |
| `render_duration{renderer}` / `degradation_count` | 渲染与可见降级 |
| `catchup_gap{source}` | 无法证明完整补齐的区间 |
| `backlog_dropped{destination}` | 显式容量丢弃 |
| `artifact_missing` / GC / backpressure | 产物完整性与容量 |
| 调度心跳、最后推进时间、关闭排干结果 | 发现调度假死 |
| 人工重投次数与结果 | 管理动作审计 |

结构化日志携带 `root_id / parcel_id / source_id / subscription_id / destination_id / 不透明 resource`，不得携带 secret。计数器重启语义、Gauge 与持久表事实必须区分；网页红点和死信记录是持久事实，进程内 counter 不是审计真相。

管理员通知区分「已生成、已尝试、已确认送达」。私聊通知是 best-effort，失败要聚合、去重并留下持久红点与日志；不能承诺故障发送链一定把通知送达。

## 6. 渲染产物与 GC

### 6.1 文件发布与引用提交

渲染产物使用内容寻址的不可变文件，队列里只放持久引用：

1. 写唯一临时文件并完成必要的落盘。
2. 原子 rename 到内容寻址路径。
3. 文件已经存在后，在一个数据库事务中写 artifact、全部 `artifact_ref`、子包裹与父结算。
4. 提交后文件才能被发送阶段视为可用。

DB 提交前崩溃只留下无引用孤儿文件；宽限期 24 小时后清理。不得先提交引用再发布文件。重试不得覆盖仍被旧包裹引用的同一路径。

live ref 文件缺失属于 `artifact_missing`：显式死信并告警，不允许发送空内容。若能从持久原始内容安全重建，可作为独立恢复动作，不能伪造原发送已成功。

### 6.2 引用生命周期

- `DELIVERING`（包括 held）与仍可重投的 `DEAD` 都是 live ref。
- `DELIVERED`、`CANCELLED`、`DROPPED` 是 settled，下一次 GC 释放。
- 原死信重投后标记 `requeued_to`，不再可重投。直接从 send 重投并复用旧 artifact 时，新 ref 与新 Parcel 同事务建立后才释放旧 ref；退回 parse/render 的新代不再引用旧 artifact，重投提交后即可对账释放，新的引用由正常文件发布事务后建。
- 显式放弃死信后才释放其最后的 live ref。年龄 TTL 与容量 LRU 都不得强删 live ref。

bison 定期通过 courier 的 `parcel_status(ids)` 批量对账，然后更新自己的 artifact_ref；不跨 schema join。运输事件可以加速释放，但周期对账才是正确性兜底。「settled 后立即删」指最迟下一个 GC 周期，不依赖一条可能丢失的进程事件。

### 6.3 容量

总容量上限 5GB。LRU 只清理无引用或已经 settled 的产物；若容量满且全部是 live ref，新渲染进入背压等待并告警，不得删除正在重试、暂停或可重投的内容。

审计元数据与二进制产物采用不同保留策略；删除文件不等于删除死信、丢弃或重投历史。

## 7. 积压与显式丢弃

24h/200 上限按**目的地**计算，覆盖该目的地所有 Source：

- 数量统计该目的地未结算内容，包括 held；held 不占活动 head，但仍受容量约束。
- 年龄从首次进入 send lane 算起；补抓窗口另按内容时间计算。
- 暂停期间仍计时计数，避免无限积压与无限持有 artifact。
- 超限保留最新内容，只把**未执行且没有 `outcome_unknown`** 的最老合格排队项原子转为 `DROPPED / backlog_exceeded` 并重建活动 head。
- 正在执行或结果不可知的最老 head 不得直接 DROPPED；允许暂时多出一个执行中的位置，等其结算后再淘汰。容量计数不得通过伪造终态维持表面上的 200。

每次丢弃记录 Source、Subscription、Destination、数量与时间范围，进入 inspect、指标与审计。`DROPPED` 是显式容量终态，不是 `DEAD`，也不是 `CANCELLED`。

不向仍故障的目的地强行发送溢出提示。持久网页提示与管理员 best-effort 通知是主路径；目的地恢复后可以发送一条去重后的聚合摘要，但摘要不承诺必然送达。

## 8. 迁移

迁移是独立插件，两个入口一份代码：`nb bison-migrate` 与 `python -m bison_migrate`。它处理旧数据映射与 datastore → orm 基础设施切换，不进入运行时。

### 8.1 安装模式与只读边界

- 全新安装与旧部署接管必须显式区分；接管模式要求提供旧库位置，不能期望在新库中发现另一个文件的旧表。
- 目标启动同时检查 schema version 与接管完成状态。
- `--dry-run` 只读并出报告，不写目标。
- 对旧 SQLite 创建一致快照，或使用能覆盖 hot journal/WAL 情况的只读方案；迁移只操作快照。WAL/SHM 相关文件必须纳入一致性处理，不能用「只执行 SELECT」推导原文件逐字节不变。

### 8.2 切流与高水位

1. dry-run 校验旧数据与目标映射。
2. 停止旧 bot，记录切流时间。
3. 立即用新 Fetcher 对每个 Source 做一次**只观察、不发送**的真实高水位快照。
4. 高水位失败的 Source 不得静默完成接管；管理员必须修复或明确接受缺口。
5. 把快照写入独立 `cutover_watermark`，并把对应 `source_post` 标为 `observed / migration_skipped`；不得推进正常运行游标，也不得生成 Parcel、`DELIVERED` 或 `DEAD`。
6. 新系统首轮用观察状态抑制高水位及之前内容重复。只有能证明晚于切流的内容才补发；无法判断先后的迟到旧内容形成补抓缺口，不能因未出现在快照中就当作新内容。

真实观察到的高水位不是伪造去重游标，而是独立接管边界。运行期游标仍只在内容成为耐久 Parcel 或 DEAD 后推进。迁移不生成任何已投递历史，也不删除旧表；`migration_skipped` 是显式迁移截断审计。

### 8.3 可重跑与完成标记

- 旧主键到新自然身份使用确定性映射。
- 每批目标写入使用 upsert/冲突校验与可恢复 checkpoint。
- 重跑不得重复创建 Source、Destination、Subscription 或 Credential。
- 全部数量、自然身份与 secret 摘要校验通过后，最后才写完成标记。
- 部分完成状态不能被启动检查误认为成功；dry-run 不写 checkpoint 或完成标记。

迁移截断是 at-least-once 的显式例外，报告必须列出每个 Source 的高水位、补抓结果与无法覆盖的区间，而不是只说「已接管 N 条订阅」。

## 9. 崩溃与验收矩阵

至少分别注入以下位置：

1. 站点尚未执行、`attempt_in_progress` 已标记、执行中取消。
2. 外部发送响应超时、断连、平台已接受但本地结果不可知，以及发送成功后统一结算前崩溃；重启时在恢复事务提交前后再次注入，side-effecting 的遗留 `attempt_in_progress` 必须先转为 `outcome_unknown` 才能重入。
3. 子包裹/去重/游标/父结算事务提交前后；业务校验拒绝必须提交父 DEAD，存储失败必须全回滚。
4. `next_poll_at` + 抓取入队，以及到期合并时 `merge_pending` + `next_poll_at` 提交前后。
5. artifact 文件 rename 后、DB 引用提交前。
6. 死信记录与 head 推进提交前后。
7. 人工重投条件更新、新 Parcel 入队，以及 send 复用或 render 重进两条 artifact 路径。
8. 发送执行中收到删除/暂停，以及第 201 条到达时最老 head 正在执行或结果不可知。
9. 关闭超时、组件资源关闭与 engine 关闭。
10. SQLite 进程崩溃；耐久声明严格限定在所选部署档案内。

每个点都要写清允许的结果是重入、无重复、可见丢弃还是等待恢复，不能用一句「不丢不重」覆盖不同边界。
