# 至少一次交付，只允许显式损失

系统采用**带显式例外的 at-least-once**：正常路径允许重入与重复尝试，不允许产生未报告的损失。它不承诺 exactly-once，也不把「绝不重复」作为验收条件。

聊天平台可能已经接受内容，而本地没有取得确定结果：包括响应超时、连接断开，以及发送成功后本地 `mark_delivered` 尚未提交时发生崩溃。重试或重启可能因此再发一次。聊天平台没有可用的幂等键，这个 **outcome-unknown** 窗口被明确接受；所有具有外部副作用的站点都必须按可重入设计并保留不可知结果审计。除此之外的重复属于缺陷，必须用精确故障注入点验收。

## 终态与覆盖缺口

- **DEAD**：当前投递代的自动运输因失败而终止。原包裹与原死信审计不被复活；管理员重投会创建带血缘的新包裹、新投递代，原死信记录其去向且不能再次重投。
- **DROPPED**：内容因明确的容量或保留策略被放弃。目的地的 24h/200 积压上限采用保留最新策略，只淘汰未执行且结果可知的排队项，并记录源、订阅、目的地、数量与时间范围；它不是处理故障。
- **CANCELLED**：删除等明确管理意图在未执行、且无不可知外部结果时终止运输。正在执行或 `outcome_unknown` 的包裹先按实际结果结算，不能伪写成未产生副作用。它不是失败，也不是容量丢弃。
- **补抓缺口**：停机或迁移后，上游已无法完整枚举的历史区间。它是源覆盖不完整的事实，不是包裹终态，也不能通过伪造死信或去重游标消除。

迁移截断、积压丢弃和补抓缺口是允许的损失例外，但必须逐源或逐目的地记录原因、范围与可确定的数量；数量无法确定时必须明确写未知。`artifact_missing` 等意外数据缺失不属于允许损失，必须形成可见故障与告警。

## Considered Options

- **宣称 exactly-once**：外部聊天发送与本地数据库提交没有共同事务，无法兑现。
- **宁可丢也不重**：把静默漏发当成降低重复的手段，违背系统的主要正确性目标。
- **把 DEAD、DROPPED、CANCELLED 与 gap 全部视为死信**：会混淆故障、管理意图、容量策略和上游覆盖能力，使审计与告警失去意义。
- **复活原死信**：破坏终态与历史审计，也无法可靠防止重复点击。

## Consequences

- 总体验收口径是：**无未报告损失；除已声明的 outcome-unknown 外部副作用窗口外无异常重复。** 「重启不重复」「全程无漏发」不能作为无条件验收语句。
- 重试属于同一投递代；重投创建新投递代与新预算根，按当前有效计划选择 fetch/parse/render/send 接入点，重新计算资源并保留原内容、自然身份与完整血缘。
- 取消、丢弃、迁移截断与补抓缺口都必须进入持久记录、inspect 与指标。网页或私聊通知失败不能把已有审计变成静默，但也不能宣称通知必然送达。
- 崩溃矩阵必须区分结算提交前后、外部发送后未结算、源入队与游标推进、死信写入和关闭超时，不能用一个笼统的「重启」测试代替。
