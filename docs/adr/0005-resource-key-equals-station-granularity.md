# 信道按资源划分，资源粒度等于站点粒度

信道键是一个不透明的**资源**字符串，规则仍是：**一个站点的资源画像就是它的风控画像 —— 需要两个画像就拆成两个站点。** 站点提供的是 `resource(parcel) -> str` 选择器，而不是注册期固定值；资源在包裹入队时计算并随该包裹冻结，转运产生新包裹时重新计算。

抓取资源可以包含 host 与**不透明的 credential id**，发送资源可以包含目的地身份。cookie、token 等 secret 绝不能进入资源键、日志、指标或 inspect。凭证在根包裹入队前选定；轮换只影响新根包裹，存量包裹保持原信道。需要让存量使用新凭证时，通过显式重投创建新投递代并重新计算资源。

## Considered Options

- **内置「凭证」概念**：courier 会因此需要理解 cookie、轮换、冷却，业务知识会渗进内核。
- **注册期常量资源**：无法让不同凭证或目的地进入各自信道。
- **执行时反复重算资源**：包裹可能在仍有旧 head 引用时换信道，破坏顺序与退避归属。
- **多资源门控**：需要锁序或原子多键获取，当前规模不支持这份复杂度。
- **抓取侧不设信道、只用一个全局令牌桶**：一个源被风控会拖慢全部源。

## Consequences

- 资源选择器是必需声明；站点答不上「我和谁共享队列」，说明它的并发约束尚未想清楚。资源值只在入队时固定，不能因 provider 后续轮换而静默改变。
- 一条信道可以承载多个地址的包裹；实现不能假设「信道 ↔ 地址」一一对应。
- **源级时间与资源级时间分离。** 直播轮询、已完结等只推后该源的 `next_poll_at`；凭证风控与资源共享节流持久化为资源的 `resource_available_at`，包裹默认失败退避留在自己的 Receipt。`Retry-After` 必须按产生它的约束归属，不能同时随意冻结两者。
- 实际执行时间是 `max(head.receipt.next_attempt_at, resource_available_at)`。资源时间跨 head、空 lane 与重启保留，不能由下一个包裹的 Receipt 重建或清零。
- 退避取默认退避与资源级 `Retry-After` 的较晚者；jitter 不得把结果提前到 `Retry-After` 以下。
- 资源太粗会让无关对象互相拖慢，太细会让同一凭证被并发请求；需要不同资源画像时仍拆站点，不引入多资源门控。
